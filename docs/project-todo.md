# RagSec project implementation checklist

Updated 2026-09-09. **Every task below is pending.** This is the execution backlog for the [roadmap](roadmap.md), from baseline setup to release and maintenance. Existing files named below are integration seams; proposed files and modules are not implemented yet.

## How to use this plan

Work in phase order, respecting the roadmap dependencies. For each checkbox, make a focused change, run its acceptance checks, and attach evidence before marking it complete. Use this completion record beside the task: `owner | commit/PR | test command and result | evidence path | limitations`. Do not commit credentials, private datasets, local databases or raw sensitive traces. Preserve upstream notices and historical documents.

The plan assumes an owned local lab, FR/EN/AR examples, synthetic users/documents and mock tools. It does not authorize deployment to external infrastructure. Security rationale is mapped to the [OWASP reference](owasp-rag-security.md); implementation details here are project design choices.

## P0 — Establish the baseline and project contract

- [ ] **P0.1 — Reproduce inherited behavior.** Inspect `requirements.txt`, `frontend/package-lock.json`, `docker-compose.yml`, `dev.sh` and `.env.example`; record tool/dependency versions and baseline revision in a proposed `benchmark/manifests/` template. Use temporary data directories and synthetic credentials. Run `python -m pytest backend/tests/ -q`, then the existing frontend build in its directory. Record failures and prerequisites without implying a clean run.
- [ ] **P0.2 — Inventory every execution branch.** Trace `backend/routes/chat.py` REST/SSE routes through `router_service.py`, `rag_service.py`, `chatbot_service.py`, `groq_service.py` and `cache_service.py`. Include fast facts, timetable answers, history, provider retries, cache hits and administration preview/download/rebuild/delete routes. Add a call-path table to `ARCHITECTURE.md`; each branch needs a planned gate and regression case.
- [ ] **P0.3 — Define the resource access matrix.** Create two synthetic tenant scopes, two ordinary actors and an administrator, with public and private documents. Specify read, ingest, approve, delete, tool and memory grants; decide whether campus-wide material is copied into each tenant collection. Keep corpus-management rights separate from unrestricted private-data reading. Persist membership on the server; never derive it from a prompt, class label or unchecked email domain. Acceptance: a table of explicit allow and deny examples approved as the implementation contract.
- [ ] **P0.4 — Freeze experiment contracts.** Create versioned case/manifest schemas under `benchmark/` and fixture directories under `attacks/`. Include case IDs, preconditions, language, artifact hashes, authorized behavior and objective oracle. Make a few benign FAQ/timetable and adversarial canary cases first. Define separate baseline/protected processes and resettable SQL, Qdrant and Redis state; verify no request parameter switches modes.
- [ ] **P0.5 — Set initial limits and ownership.** Record configurable request bytes, parser duration/memory, retrieval tokens, generation tokens, tool steps, concurrency and per-actor budget values in a proposed configuration table. Treat initial values as lab settings to test, not OWASP-approved thresholds. Assign an owner for every phase and record unresolved scope decisions.

## P1 — Build security contracts and authorization

- [ ] **P1.1 — Define typed contracts.** Add proposed `gateway/contracts.py` models for actor context, action/resource references, security outcomes, chunk references and validated responses. Carry request ID and policy/corpus/access versions. Reject extra privilege-bearing fields and malformed IDs. Test serialization, missing fields and prompt-supplied role/tenant attempts.
- [ ] **P1.2 — Connect authoritative identity.** Adapt `backend/services/auth_service.py` and chat dependencies to load current membership/grants from application records. Add reviewed Alembic migrations under `backend/alembic/versions/`; examine existing revision heads before extending them. Test disabled users, expired tokens, role revocation and conversation ownership. SQLite fixture behavior must not hide PostgreSQL migration failures.
- [ ] **P1.3 — Integrate OPA.** Add a bounded policy client in `gateway/` and explicit rules/tests in `policies/data_access.rego`. Construct policy input from authenticated context and authoritative resource records. Accept only a well-formed explicit allow, with known policy version. Test allowed reads, cross-scope denial, absent metadata, unavailable OPA, malformed JSON and unexpected decision types. Keep tool/memory stubs denied until P6.
- [ ] **P1.4 — Create offline boundary doubles.** Under `tests/`, add fake provider, retriever, clock and side-effect recorder. Use real policy evaluation for a separate OPA integration lane. Prove a denial prevents the underlying operation; a mocked allow-only adapter is insufficient evidence. Run strict Rego checks and tests alongside relevant Python tests.

## P2 — Build one protected request and response path

- [ ] **P2.1 — Introduce the shared pipeline.** Add a proposed `gateway/pipeline.py`; make both chat routes adapt its typed outcomes. Centralize identity, limits, inspection, authorized work and final release. Map all P0.2 branches, including structured answers, through it. Leave protected caching off. Compare REST/SSE outcome, source IDs and policy reason codes on identical fixtures.
- [ ] **P2.2 — Implement bounded inspection.** Build scanner contracts and normalization in `scanners/` for prompt, document, history and tool-result inputs. Keep original hashes and a normalized inspection view; bound Unicode/encoding expansion and recursive decoding. Include French accents, Arabic text, invisible characters, security discussions and oversized payloads. Pattern findings are signals and cannot grant permissions.
- [ ] **P2.3 — Isolate generation and retries.** Wrap inherited provider calls so tests can replace them without network access. Apply deadlines and cancellation to all attempts under one total budget. Before P4, allow only explicitly synthetic/public fixture context. Inject mandatory-control failures and assert no alternate provider or model-only fallback bypasses the pipeline.
- [ ] **P2.4 — Establish output gating now.** Add a full-candidate validator in `scanners/` and release adapter in `gateway/`. Buffer the answer before REST body or SSE answer events; validate synthetic secrets, configured sensitive fields and response schema. Test secrets split across provider chunks, refusal bodies, exceptions, oversized output and disconnects. SSE may send safe status events, but no unvalidated answer text.
- [ ] **P2.5 — Enforce request budgets.** Integrate actor-based limits with `backend/services/limiter_service.py`; cap concurrent generation and accumulated token/tool budgets. Define shared-store failure behavior explicitly rather than accidentally allowing unlimited work. Test concurrent requests, retry exhaustion and actor isolation with a fake clock.

## P3 — Implement ingestion and index lifecycle

- [ ] **P3.1 — Add authoritative document records.** Use PostgreSQL/Alembic for document versions, uploader, source identifier, approval, classification, tenant, access version, original hash, extraction hash, chunk hashes and parser/embedding versions. Define staged → scanned → approved → indexed → revoked/deleted transitions. Prohibit search visibility before publication. Test invalid transitions and duplicate upload idempotency.
- [ ] **P3.2 — Isolate PDF extraction.** Adapt admin upload handling to stage files under generated IDs outside served paths. Execute parsing in a restricted worker/container with no provider credentials, no outbound network, bounded CPU/RAM/time and limited temporary storage. Test malformed/encrypted PDFs, file-type mismatch, traversal filenames and extraction expansion using owned fixtures; timeout must leave no searchable content.
- [ ] **P3.3 — Build review and quarantine.** Implement source registration and scan records in `rag/`; expose administrator review through `backend/routes/admin.py`. Record reviewer, decision and exact document version; approval does not change ACLs. Test that downloads/previews also authorize access and that quarantined files cannot leak through preview, rebuild or direct retrieval.
- [ ] **P3.4 — Make index publication recoverable.** Adapt `backend/scripts/rebuild_faq_index.py` and `rag_service.py` to build a versioned staging collection from approved records. Store per-chunk provenance and permissions; validate counts/hashes before switching the active corpus reference. Retry failed jobs idempotently and preserve the prior approved index on failure. Verify an interrupted build never becomes active.
- [ ] **P3.5 — Separate index writers from readers.** Give the protected query service read-only access and the ingestion worker narrowly scoped write access. Verify the chosen Qdrant deployment supports the intended separation; use an isolated service boundary if its credential model cannot express it. Test writes attempted through the query identity and audit legitimate insert/update/delete jobs. Record embedding model/revision and protect stored vectors with the same sensitivity as their source.

## P4 — Retrieve and assemble authorized evidence

- [ ] **P4.1 — Implement scoped retrieval.** In a new `rag/` adapter, resolve collection names from server membership, then apply classification/resource filters before requesting similarity results. Start with separate fixture tenant collections; require metadata on every chunk. Recheck returned IDs with authoritative records and OPA before model context assembly. Cross-tenant queries must produce no unauthorized content, IDs or scores at the provider/client boundary.
- [ ] **P4.2 — Verify provenance and freshness.** Compare returned chunk content/version/hash against the trusted SQL ingestion manifest, not a hash supplied only by Qdrant. Check parent document status and current grants. Test altered text, forged metadata, orphan chunks and missing manifests; quarantine mismatches and emit sanitized evidence. A hash proves consistency with the trusted record, not that content is truthful.
- [ ] **P4.3 — Assemble bounded context.** Build one context object containing authorized chunks, IDs and explicit untrusted-data delimiters; reserve room for trusted instructions and answer tokens. Cap per-source contribution and total history/retrieval size. Test multiple individually innocuous chunks forming an attack, flooding and multilingual near-matches. Delimiters help the model but are not an authorization boundary.
- [ ] **P4.4 — Control provider disclosure.** Inspect the full outgoing payload, including history, retrieved content and future tool results, against allowed data classes. Keep credentials and disallowed fixture secrets out of provider requests. Spy on exact provider input to verify cross-scope and sensitive-history cases. Record provider configuration and unresolved retention questions in deployment documentation.
- [ ] **P4.5 — Close alternative data paths.** Apply equivalent resource checks to timetable/database lookups and document preview/download paths identified in P0.2. Distinguish successful empty retrieval from retrieval failure. Test that neither an unavailable vector service nor denied policy causes the inherited fallback to answer a knowledge request from model memory.

## P5 — Complete citations, cache, deletion and user flows

- [ ] **P5.1 — Validate source references.** Extend response schemas with server-built citations tied to retrieved IDs and versions; reject fabricated or unauthorized model references. Add a verification endpoint that authorizes the requesting actor before returning source metadata. If signed citation envelopes are implemented, bind answer digest, document hashes, scope, expiry and key ID; test tampering, replay and key rotation. Citation integrity does not establish factual entailment.
- [ ] **P5.2 — Enable protected caching deliberately.** Add a separate namespace to `cache_service.py` keyed by actor/scope, access/policy/corpus versions, model/prompt configuration, query and relevant history digest. Cache only eligible validated answers and their source dependencies. On hit, reauthorize dependencies and run the release gate. Test two actors asking the same question, policy changes, poisoned-source revocation and Redis failure. Keep sensitive responses uncached.
- [ ] **P5.3 — Implement revocation before asynchronous cleanup.** Mark source versions inaccessible in the authoritative store first; invalidate release/cache eligibility immediately. Queue idempotent removal of source files, chunks, embeddings and derived artifacts, with retries and an orphan sweeper. Define retention for audit metadata separately. Test failed cleanup, restart/retry, document expiry and permission changes.
- [ ] **P5.4 — Cover in-flight races and restore.** Recheck source/access versions at the final release boundary; define an atomic authorization/version strategy so release cannot race a completed revocation. Test paused generation and cache fill across revocation. Track deletion tombstones so a restored snapshot cannot reactivate deleted data; physical backup expiration is a separate documented lifecycle.
- [ ] **P5.5 — Update the demo UI.** Adapt `frontend/src/lib/api.ts`, chat state, `MessageBubble.tsx`, types and FR/EN/AR messages to show consistent blocked/unavailable/no-evidence states and authorized citations. Keep raw HTML disabled; constrain link protocols and prevent remote images from creating exfiltration requests. Add admin staged/review/quarantine/deletion states. Build and smoke-test REST/SSE, right-to-left display and citation access after logout/revocation.

## P6 — Add bounded agents, tools and memory

- [ ] **P6.1 — Add LangGraph behind the pipeline.** Introduce pinned dependencies only when implementing a graph with explicit retrieve, generate, propose-tool, authorize, execute and validate states. Set step/time/token limits and terminal outcomes. The graph receives immutable actor references, not credentials or raw database clients. Test loops, malformed transitions and cancellation.
- [ ] **P6.2 — Implement mock tool authorization.** Create a registry with read-only synthetic tools first, strict argument schemas and host-owned resource resolution. Extend `policies/tools.rego`; authorize each exact operation immediately before execution. Test unknown tools, extra arguments, changed resource IDs, policy outages and malicious returned text. Assert denied-operation side-effect counters stay zero.
- [ ] **P6.3 — Design future consequential operations.** Keep real writes/external side effects disabled until individually scoped. For a future enabled high-risk tool, bind user confirmation to action, exact arguments, actor, expiry and single-use request ID, then reauthorize execution. Test replay and argument substitution with mocks. Add destination/path allowlists and execution isolation for each capability rather than a generic shell/HTTP tool.
- [ ] **P6.4 — Implement memory as owned records.** Distinguish existing conversation history from new persistent agent memory. Add schema, provenance, access version, expiry and read/write/delete operations behind `policies/memory.rego`. Store remembered text as untrusted data. Test cross-user reads, poisoned writes, deletion, revoked ownership and attempts to persist privileged instructions.
- [ ] **P6.5 — Preserve experiment parity.** Supply identical graph, mock tools and memory functionality in both lab arms, with RagSec controls differing only as declared by the manifest. Preserve inherited authentication in both. Test fixture resets and ensure benchmark-only mode cannot be reached from the normal gateway.

## P7 — Prepare operations and deployment

- [ ] **P7.1 — Add safe request traces.** Extend `logging_service.py` and proposed audit storage with request/actor IDs, stage, resource references, decision versions, durations and reason codes. Use opaque IDs or keyed query digests rather than raw prompts. Define restricted evidence access and retention. Trace cache hits and tool calls; assert fixture secrets never appear in normal logs, exceptions or metrics labels.
- [ ] **P7.2 — Detect corpus anomalies.** Add scheduled comparisons of active Qdrant records to approved manifests, collection-size changes and orphan counts. Record embedding-version shifts and retrieval distribution changes using synthetic probes. Establish a lab baseline before selecting alert thresholds; do not present anomaly detection as proven embedding-attack prevention.
- [ ] **P7.3 — Rehearse an incident.** Write a runbook to disable a poisoned version, invalidate dependent caches, identify affected response IDs, rebuild from approved records and verify recovery. Rehearse with synthetic poison and a tampered index. Assign an operator and capture sanitized drill evidence; fail recovery if stale citations, cache entries or restored snapshots resurrect the version.
- [ ] **P7.4 — Build the protected deployment profile.** Add separate Compose services/configuration for gateway, OPA and parser/ingestion workers. Bind lab listeners to loopback, isolate data services, use non-root containers and keep credentials outside images/Git. Configure service authentication and intended encryption/storage controls; document TLS and provider egress for any later remote deployment. Health/readiness must not report a protected service ready while mandatory policy checks fail.
- [ ] **P7.5 — Establish update and backup procedures.** Inventory Python/npm/container/parser/embedding dependencies and any future connector owners/credential references. Pin reproducible releases, scan dependencies, stage model/index migrations and rehearse rollback. Verify backup restore against current ACLs and deletion tombstones. External connectors remain disabled until scoped credentials and staging tests exist.

## P8 — Evaluate and release the complete project

- [ ] **P8.1 — Complete the offline security matrix.** Add suites in `tests/` for poisoning, combined-chunk injection, cross-scope access, stale grants, cache isolation, unauthorized tools, citation tampering and cascading deletion. Include outages, cancellation and positive authorized cases. Extend `.github/workflows/main.yml` with secret-free offline provider doubles, Python firewall tests and strict OPA checks; retain `backend/tests/` regression and frontend build jobs.
- [ ] **P8.2 — Implement paired evaluation.** Build the executable harness under `benchmark/` using P0 schemas and the existing protocol. Randomize run order, reset state, separate warm/cold cache, record model nondeterminism and count setup errors/timeouts separately. Use canary matches and executed mock side effects for deterministic objectives; adjudicate ambiguous poisoned-answer cases with a written rubric.
- [ ] **P8.3 — Freeze held-out evaluation.** Add FR/EN/AR attack and matched benign cases in `attacks/`, partition development/held-out IDs before tuning and hash all artifacts. Predeclare repetition count and acceptance thresholds for benign quality, false positives and latency. Run live models only as explicit versioned experiments; offline mocked results must not be reported as live protection rates.
- [ ] **P8.4 — Publish evidence and limitations.** Produce a report under `benchmark/` with counts, denominators, confidence intervals, per-category attack success, benign task success, false positives, latency and availability failures. Include per-control ablations and sanitized failure cases. Report unsupported/unrun scenarios as such; never substitute the README's illustrative numbers.
- [ ] **P8.5 — Finish the product handoff.** Walk through benign chat, denied retrieval, poisoned upload review, mock tool denial and source deletion in the frontend. Update active README, architecture, threat model, testing instructions and component READMEs with source/test references. Check clean-clone setup, migrations, recovery and provenance notices. Make a release only after its declared scope passes the gates; document residual risk and deferred capabilities.

## P9 — Optional research and continuing maintenance

- [ ] **P9.1 — Evaluate optional classifiers.** Compare deterministic-only and classifier-assisted modes on frozen data with separate development tuning. Measure false positives by language, objective prevention and added latency. Specify whether a classifier is optional or mandatory per deployment; its output never overrides policy denial, and its outage behavior needs tests.
- [ ] **P9.2 — Evaluate embedding and storage alternatives.** Use versioned corpora to compare embedding drift, alternate models and, if needed, pgvector against Qdrant. Measure retrieval quality, isolation, operations and migration costs. Treat multi-model checks or embedding privacy techniques as experiments; adopt only with evidence and a threat-model update.
- [ ] **P9.3 — Maintain the release.** Assign dependency review and retention-job schedules, rerun regression after policy/model/parser/corpus changes, and repeat incident/restore drills. Revisit the OWASP mapping on reference updates. Turn newly observed failures into development cases while preserving an untouched held-out set for subsequent evaluation.

## Final acceptance checklist

- [ ] Each shipped boundary has both an allowed-case test and a denied/failure-case test.
- [ ] REST, SSE, cache, fallback, tool and memory paths have no unchecked release or execution branch.
- [ ] Baseline regressions, firewall tests, Rego checks and frontend checks have recorded current results.
- [ ] Benchmark conclusions link to manifests and distinguish live runs from offline assertions.
- [ ] Deployment, rollback, incident handling, retention and known limitations have named owners and reviewable evidence.
